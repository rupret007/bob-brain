### 1. Proposal-ID Action Cards (app.py / job_queue.py / test_webchat.py)

**Issue — Stale-ID logic has a blind spot:**
```python
if job_proposal and expected_job and job_proposal != expected_job:
```
When `expected_job` is `None` (no `pending_job_id` in conversation), the condition short-circuits and falls through to generic confirmation handling. A stale proposal ID can be silently ignored if the pending ID was never set.

**Fix:** Reject if `job_proposal` is supplied but does not match `expected_job`, regardless of whether `expected_job` is present:
```python
if job_proposal and (expected_job is None or job_proposal != expected_job):
    # reject
```

## Supporting Evidence and Proposed Changes

1.  **Proposal-ID Action Cards:**
    *   **Issue:** The `app.py` logic for rejecting stale proposals (`if council_proposal and expected_council and council_proposal != expected_council`) is flawed. It fails to reject a stale proposal if `expected_council` (or `expected_job`) is `None`, allowing a user to confirm *any* proposal if the system has lost track of the pending one. This creates a bypass for the intended security.
    *   **Proposed Change:** Modify `app.py` to reject a supplied `proposal_id` if `expected_job` (or `expected_council`) is `None` but a `job_proposal` (or `council_proposal`) is present. Also, ensure `pending_job_id` and `pending_council_id` are cleared consistently when the corresponding `pending_job` or `pending_council` is cleared.

2.  **Explicit Changelog Field:**
    *   **Issue:** The `round_changelog` function in `webchat/app.py` introduces `round_num` which uses `re.search(r"R(\d+)", path.name)` for sorting. This is fragile; if the filename format changes, sorting will break. The `test_webchat.py` only asserts presence of "proposal" in the line, not the correct extraction of the changelog itself or its robustness to various formats.
    *   **Proposed Change:** Strengthen `test_webchat.py` to include tests for different changelog formats (section, explicit, fallback) and ensure correct extraction and sorting.

3.  **Drill SHA Hygiene & Isolated Drill Fixture:**
    *   **Issue:** The change `DRILL_COMMIT_SHA = "drill0001"` in `webchat/live_handback_drill.py` is a cosmetic change and **does not provide isolation**. The drill still writes to and reads from the production `root` and `conductor/handback/HANDBACK-LOG.md`, as evidenced by `ledger_round(root: Path, tag: str)` and `main()` reading `ROOT / "conductor/handback/HANDBACK-LOG.md"`. This directly violates the P0 requirement for drill isolation and risks contaminating real status. `drill0001` is also not a valid Git SHA.
    *   **Proposed Change:** Implement a temporary fixture root for all drill operations in `webchat/live_handback_drill.py` to ensure no production files are touched. Use a truly synthetic identifier for drill SHAs or generate a temporary Git repository for testing SHA handling.

4.  **Public Live_Ops Dashboard Fields:**
    *   **Issue:** `test_services.py` only asserts `dashboard_freshness_seconds` and `roles` are *present* in the public output, not that their values are correct or that `dashboard_freshness_seconds` is a valid numeric value.
    *   **Proposed Change:** Add assertions in `test_services.py` to verify the *values* and *types* of `dashboard_freshness_seconds` and `roles` after `public_live_ops()` processing.
