## Minimal safe implementation

Leave the active texting candidate frozen. Make the successor tooling change in the gaps preparation worktree, then merge it forward with each subsequently released feature. Prefer one shared release specification and common runner/launcher functions over five hand-maintained copies of the recovery logic. Keep the existing texting entry points as compatibility wrappers so past evidence and its counter remain interpretable.

Use a validated release specification with these fields: feature, stable release series, exact branch, exact allowed lane, receipt prefix, full expected predecessor SHA, prior successful deployment record path and hash, and maximum activations. The candidate SHA remains the actual clean `HEAD`, checked against the draft PR, remote branch and equal-tree clean merge. Store the specification bytes/hash and predecessor identity in every new deployment record and its recovery journal. Reject unknown feature/series combinations, path escapes, inconsistent predecessor records, and a changed specification on resume. Do not allow an arbitrary command-line series to evade the retry limit.

Suggested identities are `2055` for the existing texting release and `2055-gaps`, `2055-media`, `2055-instinct`, `2055-voice`, `2055-ui` for the successors. Use receipt prefixes such as `GAPS-2055`, `MEDIA-2055`, `INSTINCT-2055`, `VOICE-2055`, `UI-2055`. Keep stable names only as verified pointers to immutable SHA/attempt evidence; failed or partial output must never replace a passing alias. The existing isolated harness already accepts `--root`, `--candidate`, `--output` and `--timeout`, so each run can write an exclusive attempt-specific path and promote it only after `verify_proof` succeeds.

Count each release series' records with `activated=true`, including activations that fail startup, replay or final publication and are rolled back. Do not charge review reservations, offline checks, private replay attempts, or preflight exits that never activated. Record and enforce a maximum of five activations per feature across all its candidate SHAs. Preserve texting's existing activated history when reading legacy `WEBBOB-TEXTING-DEPLOYMENT-0927-attempt*.json` records; changing a filename or branch must not erase that count. Keep audit slot numbers separate from activation counts, with collision-resistant exclusive reservations under the supervisor lock. The activation limit is a ceiling, not permission to misclassify a real quality failure as tooling or relax a gate.

For a successor baseline, first verify the predecessor's final successful deployment receipt and hashes, then authenticate local and public `/api/version` and require the same full SHA. Verify both running code pins and their build manifests agree. A mismatch is a HOLD, not permission to redefine the predecessor as whatever is currently running. The successor's rollback snapshot is a fresh copy of those current verified pins; snapshot manifests must name that immediate predecessor. Persist the intended rollback directory and recovery reserve before activation. Both child and parent emergency recovery must restore and verify this predecessor even if final report publication fails or the mutable release record cannot be read.

After a successful release, prune ignored dependency/build caches only where proof verification does not depend on them; keep saved results, session/queue evidence, validation logs, local publication receipts, commits and bare refs. Never treat `/private/tmp` as extra disk capacity. On tooling failure, preserve failed attempt evidence, repair the identified defect, regenerate every invalidated exact-tip receipt, and retry within that feature's remaining activation allowance. A real quality failure remains a failed gate.
