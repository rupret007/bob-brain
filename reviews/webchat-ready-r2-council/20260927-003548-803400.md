### Codex
**Best recommendation:** Fix job authorization before enabling READY queue writes. Calling a request “draft” does not prevent the scheduler from executing it.

1. **Critical — job confirmation bypasses the refusal check.**  
   In `conductor/webchat/app.py`, `Chat.submit()` handles job creation and confirmation before `hard_rule_refusal()`. `start job: merge PR #123` followed by `yes, start job` therefore reaches `queue_draft()`. In `job_queue.py`, `CONFIRM` also accepts `yes, start job, but do not run it`, and every task becomes `non-coding | READY`; `duplicate_task()` only searches screen-listing text and does not enforce one coder.  
   **Fix:** Validate the stored task before proposing and again before queueing; require an exact confirmation tied to that task; enforce coder occupancy explicitly.  
   **Required tests:** Forbidden task wrapped in `start job`; qualified/negated confirmation; coding task while a coder is active; concurrent queue writers preserving both INDEX rows.

2. **High — handback can misdate and fabricate ledger entries.**  
   In `conductor/webchat/handback.py`, `refresh_summary()` parses CT timestamps as naive datetimes, so `.timestamp()` uses the host timezone. On a UTC host, cutoff filtering shifts by five or six hours. `append_turn()` embeds raw multiline asks; an ask containing `\n## <timestamp>\n` becomes a separate block on the next parse. `public_digest()` also rewrites the summary on every panel read, making its modification time reflect polling.  
   **Fix:** Use timezone-aware structured records, render user text as quoted data, and separate read timestamps from content-update timestamps.  
   **Required tests:** UTC versus Chicago hosts, DST boundaries, forged headings, and repeated reads preserving content-update time.

3. **Medium — frontend state prevents read-aloud and misreports actions.**  
   In `conductor/webchat/static/app.js`, `render()` returns on unchanged `revision` before speaking; tapping Speak on an already displayed answer does nothing. Every action card says “No action executed,” including successfully queued jobs. On mobile, an outstanding microphone result appends to the shared composer even after switching conversations.  
   **Fix:** Speak directly from the selected answer, render action-card state accurately, and cancel recognition when switching chats.  
   **Required tests:** Speak after completed polling; queued-card wording; switch chats during dictation; panel refresh failure must visibly mark retained data stale.

## Final plan (Round 2 webchat)

### 1. Most reliable design

Treat Web Bob’s job path as **two-step authorization**, not chat copy: parse a task, run the same **hard-rule and occupancy checks** you would before any `next-prompts` write, store a **versioned pending intent** (id + description hash + expiry), and only queue on an **exact, bound confirm** that clears or invalidates pending on any other submit. Handback should be **append-only structured data** (timezone-aware timestamps, user text that cannot spawn `## ` log sections) with **read paths that do not rewrite digest files** on every `/api/panel` poll so mtimes mean “content changed,” not “Jeff opened the panel.” The UI should drive speak/mic off **explicit user actions and conversation id**, not full-conversation JSON revision equality.

### 2. Top 3 fixes (ranked)

**1. `conductor/webchat/app.py` — job path before `hard_rule_refusal` + stale `pending_job` + misleading confirm logging**

**Change:** Validate `pending_job` (and confirm text) with `hard_rule_refusal` (and task policy) **before** the confirm card and again before `queue_draft`; replace free-text confirm with binding to `pending_job_id`/hash; clear or expire `pending_job` on every non-confirm submit; set `confirmations` only when `result["ok"]`, log refusals/blocks separately.
