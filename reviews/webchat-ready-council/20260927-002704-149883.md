### Ranked Issues

**1. CRITICAL: Gemini/MiniMax intentionally bypass lane locks but no test documents this design constraint.**

In `providers.py` `call()`, the lane context manager wraps only `codex`, `cursor`, and `claude`. Gemini and MiniMax call `api_call.py` directly with no lock. The README states this is intentional, but no test verifies:
- `test_gemini_minimax_skip_lane_lock` — confirm these providers never acquire a lane
- `test_busy_parallel_providers` — what happens when multiple lanes are busy simultaneously (current `test_busy_cli_lane_falls_through_to_next_provider` tests one busy provider only)

**2. Race condition in per-conversation worker launch.**

In `app.py` `submit()`, the code checks `if identifier in self.workers` under lock, then calls `launch()`. However, `complete()` (the worker target) acquires `self.lock`, modifies message status to "running", saves, then releases. If `sweep_stuck()` runs between the worker's status update and its `workers.pop()`, the stale worker entry could cause the next `submit()` to get a false 409.

Fix: In `complete()` `finally`, the `self.workers.pop()` should use the identifier passed from `launch()`, not re-fetch from `self.workers`.

**3. Mobile UX: No dedicated Send button visible on phones, conflicting with README.**

The README says "On a phone, use Send," but the mobile CSS (`@media (max-width: 540px)`) only styles the existing submit button — it doesn't create a distinct large Send button. The current implementation shows the same Enter-to-send behavior on all form factors. Missing test: `test_mobile_send_button_visible` checking that a tap target exists without needing keyboard focus.

**Top 3 Ranked Concrete Fixes:**

1.  **Bug: Race condition in `Chat.submit` and `Chat.launch` leading to duplicate worker creation.**
    *   **Evidence:** `app.py`, lines 236-237: `if identifier in self.workers: raise RequestError(409, "Bob is finishing another reply in this conversation. Stop it or wait, then try again.")` and lines 243-245: `self.launch(identifier)` are within the same `with self.lock:` block, but `self.launch` itself starts a new thread. While `self.workers` is checked, the `launch` function immediately starts a new thread, and the `complete` function (run in the new thread) then re-acquires the lock to update the conversation status. There's a window where `self.workers` could be updated by `launch` before `submit` fully exits, or another `submit` call could check `self.workers` after `launch` has started but before the `complete` thread has fully acquired the lock and updated the conversation state. This could lead to multiple workers for the same conversation if `submit` is called rapidly.
    *   **Fix:** The `launch` function should be responsible for adding the worker to `self.workers` *before* starting the thread, and this operation must be protected by `self.lock`. The `submit` function should only call `launch` if `identifier` is not in `self.workers`.

2.  **Missing Test: Direct Gemini/MiniMax API calls without lane locks are not explicitly tested for concurrency.**
    *   **Evidence:** `api_call.py` explicitly states "Metered Gemini/MiniMax calls for web chat without conductor lane locks." The `providers.py` `call` method for `gemini` and `minimax` does not use `self.lane(provider)`. While `failover.py`'s `Circuit` handles `acquire`/`release` for providers, the explicit statement in `api_call.py` about "without conductor lane locks" suggests a potential for contention if the underlying `bin/ask-gemini.sh` or `minimax` scripts are not themselves designed for concurrent execution from multiple `api_call.py` instances. The current `test_webchat.py` does not have a test case that specifically asserts that multiple concurrent `api_call.py` executions for Gemini/MiniMax do not interfere with each other or cause unexpected behavior.
    *   **Fix:** Add a test case in `test_webchat.py` that simulates multiple concurrent `api_call.py` invocations for Gemini and MiniMax and asserts their independent operation and correct output. This would involve mocking `subprocess.run` to simulate concurrent execution and verifying no shared state corruption.

3.  **Bug: Mobile UX: `composer` padding for `env(safe-area-inset-bottom)` is applied twice.**
    *   **Evidence:** `style.css`, line 72: `.composer { ... padding-bottom: max(10px, env(safe-area-inset-bottom)); }`. `style.css`, line 84: `@media (max-width: 540px) { ... .composer { padding: 6px; ... padding-bottom: max(10px, env(safe-area-inset-bottom)); } }`. The `padding-bottom` is defined in the general `.composer` rule and then *redefined* in the media query. While the `max` function might mitigate some issues, it's redundant and could lead to unexpected padding behavior or double application if not handled carefully by the browser's CSS cascade.
    *   **Fix:** Remove the redundant `padding-bottom` declaration from the media query in `style.css`. The general rule for `.composer` should suffice, or the media query should explicitly override it if a different `max` value is intended for smaller screens.
