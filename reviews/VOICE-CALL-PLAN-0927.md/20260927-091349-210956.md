### gemini-2.5-flash
PROPOSAL:

My best recommendation is to implement a WebRTC-based voice call mode using a Python backend on the Mac mini, leveraging local streaming STT (sherpa-onnx) and TTS (macOS built-in `say` command or `AVSpeechSynthesizer` via a Python bridge), with a focus on low-latency, barge-in, and local-first operation.

**Architecture:**

*   **Client (iPhone Safari):** HTML5/JavaScript using `MediaDevices.getUserMedia()` for microphone access and `RTCPeerConnection` for WebRTC audio streaming (Opus codec). A simple waveform button initiates the call.
*   **Server (Mac mini - Python):**
    *   **WebRTC Signaling:** A small FastAPI or Flask server handles WebRTC signaling (SDP exchange, ICE candidates) over Tailscale HTTPS.
    *   **Audio Processing Pipeline:**
        *   **WebRTC Endpoint:** Receives Opus audio from the client, decodes it to PCM.
        *   **VAD:** Uses a lightweight, local Voice Activity Detection (VAD) library (e.g., `webrtcvad` or a small ONNX model) to detect user speech.
        *   **STT:** Feeds PCM audio segments to `sherpa-onnx` for streaming speech-to-text, generating partial and final transcripts.
        *   **LLM Integration:** The transcript is fed to a local MLX-based language model (e.g., `mlx-lm`) for generating responses.
        *   **TTS:** The LLM's response is sent to macOS's built-in `say` command (via `subprocess`) or a Python bridge to `AVSpeechSynthesizer` for text-to-speech, generating audio.
        *   **WebRTC Endpoint:** Encodes TTS audio to Opus and streams it back to the client.
    *   **Transcript Management:** Maintains a live transcript, updating it with user and assistant speech.
    *   **Tool Use:** A simple dispatcher integrates with existing local tools based on LLM output.

**Libraries:**

*   **Python:** `fastapi` (or `flask`), `uvicorn`, `aiortc` (for WebRTC), `webrtcvad` (or similar VAD), `sherpa-onnx` (for STT), `mlx-lm` (for LLM), `pyaudio` (for audio handling if not using `aiortc`'s direct audio frames), `subprocess` (for `say` command).
*   **JavaScript:** Standard WebRTC APIs.

**File Plan:**

*   `web/static/voice-client.html`: HTML for the Safari client, including the waveform button and transcript display.
*   `web/static/voice-client.js`: JavaScript for WebRTC setup, microphone access, audio streaming, and UI updates.

*   `server/tools.py`: Tool dispatcher and definitions.
*   `server/models/`: Directory for `sherpa-onnx` and `mlx-lm` models.
*   `docs/voice_latency.md`: Documentation for latency measurements and targets.

*   **Wrong:** "Whisper provides incremental windowed decoding, not native streaming recognition." *   **Missing:** Concrete details on how `voice/whisper_bridge.cpp` would integrate with Python for the rest of the pipeline. It proposes a C++ component but doesn't specify the IPC or binding mechanism (e.g., FFI, gRPC, named pipes).

*   **Unsafe:** The proposal for `voice/MacSpeech.swift` to "forward PCM callbacks through a bounded queue, resample, and stream Opus" implies custom audio processing and encoding in Swift, which adds complexity and potential for latency/bugs compared to using a more integrated WebRTC audio path.

**Cursor Proposal Critique:**

*   **Wrong:** "Libraries: Pipecat transport optional wrapper; `sherpa-onnx` *or* `whisper.cpp`/`faster-whisper`". This is a minor point, but `sherpa-onnx` *includes* Whisper models, so listing it as an alternative to `whisper.cpp`/`faster-whisper` is slightly redundant if the intent is just "use a local Whisper model." It's better to pick one or clarify the specific use case for each.
*   **Missing:** Specifics on how the "reuse Web Bob’s current agent + tool runner" would be adapted for a voice interface. Web Bob likely uses text-based input/output; the voice proposal needs to detail how tool outputs are converted to spoken responses and how tool execution impacts the conversational flow (e.g., "working on it" phrases, progress updates).
*   **Missing:** A clear strategy for handling long tool execution times within the 1.5s latency budget. It acknowledges the risk but doesn't propose a concrete architectural solution beyond "speak a fixed 'working on it' clause immediately." This needs to be integrated into the `voice_pipeline.py` or `voice_tools.py` design.
*   **Unsafe:** "SSE or WebSocket for live transcript + tool status on the same page as the waveform button." While functional, WebRTC data channels are often preferred for real-time, low-latency signaling alongside media, as they share the same connection and can benefit from WebRTC's congestion control. Using a separate SSE/WebSocket channel adds another network path to manage.

**My Changes:**

1.  **Consolidate STT:** Explicitly choose `whisper.cpp` (via `ctranslate2` or `pywhispercpp` for Python binding) for streaming STT due to its proven performance and local-first nature. This avoids the "or" choice and simplifies the stack.
2.  **Tool Integration:** Design `voice_tools.py` to explicitly handle asynchronous tool execution. When a tool is invoked, immediately send a "working on it" TTS response. Once the tool completes, synthesize its result into speech. This ensures the 1.5s first audio target is met for the acknowledgment, even if the tool takes longer.
3.  **Unified Signaling:** Leverage the WebRTC data channel for all signaling (transcript revisions, tool status, cancellation events) instead of separate SSE/WebSockets. This simplifies network management and ensures tight coupling with the audio stream.
4.  **Python-native TTS:** Use `NSSpeechSynthesizer` via `PyObjC` directly in `voice_pipeline.py` to avoid the Swift bridge complexity proposed by Codex, keeping the core logic in Python.
5.  **Concrete File Plan:**
    *   `voice-call/voice_server.py`: Handles WebRTC signaling, session management, and routes audio frames.
    *   `voice-call/voice_pipeline.py`: Orchestrates VAD, STT, LLM interaction, tool invocation, and TTS.
    *   `voice-call/voice_session.py`: Manages turn IDs, cancellation logic, and conversational state.

    *   `voice-call/voice_tts.py`: Wrapper for `NSSpeechSynthesizer` via `PyObjC`.
    *   `voice-call/voice_tools.py`: Adapts Web Bob's tool runner for voice, including spoken acknowledgments.
