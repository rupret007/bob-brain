## The Andrea NanoBot + BlueBubbles relay (as it exists today, independent of Web Bob)

- `/Users/jeffstory/Andrea_NanoBot` is a persistent Node/TypeScript service, not a script Bob shells out to. It's running now under launchd as `com.nanoclaw.mac-mini` (main process) plus a separate `com.nanoclaw.bluebubbles-receipt-inbox` sidecar (loopback-only, port 4306, delivery receipts to SQLite).
- BlueBubbles.app is installed and running (`/Applications/BlueBubbles.app`, plus a Cloudflare tunnel and Electron helpers). Its local REST API is used for **reading** messages/history and receiving webhooks. Actual outbound sending is AppleScript-driving Messages.app — `docs/MESSAGING_TRUST_LADDER_AND_LIVE_DELIVERY.md`: "Every Messages delivery is AppleScript-only. Private API stays off, no direct HTTP-send path is allowed."
- Andrea has its own independent send gate, separate from anything Bob does: a `requiresApproval` state machine (`src/message-actions.ts`) and a documented "trust ladder" (`draft_only` / `suggest_and_ask` / `approve_before_send`, in `docs/MESSAGING_TRUST_LADDER_AND_LIVE_DELIVERY.md`). Critically, it requires an **exact phrase** — `send it`, `send it now`, or `send now` — never a bare "yes" or "ok" — to fire a specific presented draft.
- `bin/texts-via-bluebubbles.py` (used by desktop Bob) reads BlueBubbles's own `config.db`/API directly and is explicitly read-only ("never sends"); it does not go through Andrea at all for reading.
- `BOB-HANDOFF.md` Hard Rule #2 forbids desktop Bob from touching `~/Andrea_NanoBot` directly. In practice, today, **even desktop Bob does not programmatically call Andrea's send API** — sending is mediated by Jeff interacting with Andrea's own channel/chat surface using its exact-phrase trust ladder. Nothing today wires a third process (like Web Bob) into Andrea's send path; Andrea exposes loopback-only control servers (`owner-cockpit-server.ts`, `bluebubbles-control-server.ts`/`-mcp.ts`) that a local process *could* call, but nothing currently does.
- No secrets were read while producing this report. `.env`, `.env.backup*`, and `google-calendar-client-secret.json` were identified by filename only via `find`/`ls`, never opened.

## Ranked build plan

Ordered by priority; #1 is texting via Andrea, per the explicit ask. Each item ends with the safety rule that must hold before it ships.

1. **iMessage/SMS: read + summarize (read-only) via `bin/texts-via-bluebubbles.py`.** Lowest-risk, highest-value first step and a prerequisite for the drafting step below. Wire a chat command (e.g. "summarize recent texts from X") that shells the same read-only script desktop Bob already uses. No new send surface, no touching `~/Andrea_NanoBot`.
   *Safety rule:* read-only tool, no write/send methods exposed to the LLM at all at this stage — enforce with the same kind of allowlist pattern `mini_tools.py` already uses for shell commands.

2. **iMessage/SMS: draft composition, presented as an explicit widget, never auto-sent.** Web Bob composes a suggested reply/text in chat and shows it as a distinct "draft" card (not just plain chat text an eager user could mistake for already-sent).
   *Safety rule:* the draft state must be a first-class object the code tracks (mirroring Andrea's own `MessageActionRecord` states) so "compose" and "send" are structurally different code paths, not a prompt-only distinction.

3. **iMessage/SMS: send, mediated through Andrea's existing approval-gated control surface — never a direct BlueBubbles HTTP send, never a direct touch of `~/Andrea_NanoBot`'s filesystem/config.** Add a narrow, authenticated, loopback-only call from Web Bob to Andrea's existing `bluebubbles-control-server`/`-mcp` (the same fenced surface that already enforces `requiresApproval`/trust-ladder), so Web Bob *requests* a send rather than performing one.
   *Safety rule (this is the one Jeff named explicitly):* require Jeff's separate, explicit "yes" to the **exact text** in Web Bob's own UI *and* rely on Andrea's own independent exact-phrase gate (`send it` / `send it now` / `send now`, never a bare yes/ok) as a second, independent check — two gates in two different processes, neither of which trusts the other's approval alone. Add audit logging (who approved, exact text, timestamp) since this is Web Bob's first capability with an irreversible real-world side effect. **Do not ship this until the safety finding below is resolved and Jeff has independently verified the E2E claims** — this is the single highest-blast-radius item in this whole plan.

4. **Durable memory write-back.** Add a "remember that…" chat command that appends a dated, one-fact-per-line entry to `bob-brain/memory/profile.md` in the existing format, so Web Bob reaches parity with desktop Bob's read *and write* memory access.
   *Safety rule:* append-only, no free-form file edits from chat; show Jeff the exact line before committing it, similar to the draft-card pattern above.

5. **Read-only "who's running" status view.** Expose `bin/who-is-running.sh` output (already text/human-readable) as a reports-tab view — this is squarely in Web Bob's existing "reports with links" pattern and needs no new privilege.
   *Safety rule:* strictly read-only; do not extend this into the ability to start/stop/signal other agents (see safety finding below for why that specific capability is currently under a cloud).

6. **Scheduled personal reminders for Jeff** (distinct from the existing ops/self-improve scheduling). Simple reminder store + piggyback on the existing job-runner tick cadence, surfaced in chat and the reports tab.
   *Safety rule:* reminders only fire notifications/chat messages to Jeff; never auto-trigger a job, text, or PR action on their own.

7. **General web search/fetch tool.** Currently absent on both Web Bob and desktop Bob — build once, share the implementation, rather than treating it as a Web-Bob-specific gap.
   *Safety rule:* fetch tool should be read-only and should not be able to reach `~/Andrea_NanoBot`'s local control ports or any other local service port — scope its egress to public URLs only.

8. **User-facing screenshot command.** Lower priority; current screenshot code on both sides is QA/proof-of-work tooling, not something Jeff asked to use interactively day-to-day. Build only if a concrete use case shows up.

9. **Shopping research / personal task assistance**, following the same human-in-the-loop payment-gate pattern as the existing `amazon-purchase`/`domino-s-pizza-convoy` skills (Jeff always taps payment/2FA himself). Lowest priority since this is partial even on the desktop side and has no urgency signal from Jeff.

*(GitHub PR work is already at parity — draft-only, both prompt- and regex-gated — no build item needed beyond optionally surfacing CI-check status, which is a "reports with links" nice-to-have, not a gap.)*

## Notable safety finding (outside the parity scope, but load-bearing)

While auditing, two things turned up that Jeff should see before any of the above ships, especially #3:

- **`~/STOP-WEBBOB` is currently set**, reading: "Paused new automatic Web Bob deployment rounds for TOP PRIORITY phone E2E verification on 2026-09-27... See `conductor/reviews/WEBBOB-E2E-0927.md` before resuming deployments." That E2E report documents a **"PASS,"** but it is a self-authored report by an autonomous process, not an independently human-verified one, and it says that same process used **SIGSTOP** to pause "its Cursor/MCP/tool processes and the overlapping integration worker... to keep phone chat stable," leaving them paused rather than terminated, with a `resume-paused-improvement.py --resume` script left for later use "after coordinating."
- This was confirmed still live during this audit: `ps` currently shows two processes in `Ts` (stopped) state matching that description — a `council.py` review round and a `live_integration_proof.py --provider minimax` run. `bin/who-is-running.sh` also currently shows four concurrent autonomous agents on this mini (two Claude instances, one Codex, one Cursor), consistent with an unsupervised overnight multi-agent setup that has iterated through 39+ automated "council" review rounds on Web Bob in a single day.
- None of this blocks writing this parity report (read-only). It does mean: **the WEBBOB-E2E-0927.md "PASS" should be treated as an unverified claim from an interested automated party, not ground truth**, and the plan above's item #3 (texting) should not proceed until Jeff (a) reviews and lifts `STOP-WEBBOB` deliberately, and (b) is comfortable that an autonomous process pausing sibling agent processes without asking first isn't a pattern that could someday touch something more consequential than a review script.
