Based on an audit of the repository, this report outlines findings and an implementation plan for the ongoing "Web Bob integrate" task. As the original task prompt was not recorded, this analysis is derived from the current state of the code, particularly the new Web Bob dispatch system.

### Audit Findings

The "Web Bob integrate" task appears to be the implementation of a durable, resilient task dispatch system originating from the web chat interface. This system replaces a simple request/reply model with a persistent queue, allowing for asynchronous, multi-provider job execution managed by the backend services.

**Strengths:**

1.  **Resilience:** The core of the new system is `state/task_queue.py`, which implements a durable, append-only task queue (`conductor/state/queue.jsonl`). This, combined with claim tokens and worker heartbeats managed by `services/dispatch_worker.py`, ensures that tasks are not lost if the server or a worker restarts.
2.  **Decoupling:** The architecture decouples the web front-end from the job execution back-end. `webchat/app.py` now acts as a client that enqueues tasks, and `services/job-runner.sh` (via `services/web_dispatch.py`) polls this queue to launch workers. This is a significant improvement over a synchronous model.
3.  **Security and Capability Scoping:** The introduction of API-only workers (`services/api_worker.py`) for tasks like audits and reviews is a strong design choice. It provides models with necessary repository evidence without granting them file system or command execution capabilities, adhering to the principle of least privilege. Tool-capable workers (`codex`, `cursor`) are reserved for tasks that explicitly require file system writes.
4.  **Result Verification:** The `services/result_acceptance.py` module introduces a crucial gate. It programmatically rejects common failure modes (empty answers, refusals, blockers) and uses a semantic self-review to confirm task completion, which increases the reliability of "successful" job outcomes.

**Areas for Improvement & Risks:**

1.  **Dual Job Systems:** The repository now contains two distinct job systems: the legacy system managed by `services/jobs.py` (using `conductor/jobs.jsonl`) and the new Web Bob system (`state/task_queue.py`). This creates complexity and potential for confusion. The legacy system appears to handle scheduled project work, while the new system handles interactive requests from the web chat. A clear plan to unify or formally separate these is needed.
2.  **State Management Complexity:** State is spread across multiple locations: `conductor/jobs.jsonl`, `conductor/state/queue.jsonl`, and `conductor/state/STATE.json` (via `state/ledger.py`). While each serves a different purpose, their interaction is not immediately obvious and could be a source of bugs.
3.  **Missing Centralized Task View:** The UI (`webchat/jobs_view.py`) needs to present a unified view of both legacy and new jobs to provide a complete operational picture. Currently, it appears to be evolving towards this but may not be complete.

### Implementation Plan

The following plan focuses on solidifying the integration, unifying the user experience, and reducing technical debt from the dual job systems.

1.  **Unify the Jobs View:**
    *   **Task:** Modify `webchat/jobs_view.py` and its data source `webchat/ops_panel.py` to read from both `conductor/jobs.jsonl` (legacy) and `conductor/state/queue.jsonl` (Web Bob).
    *   **Details:** Create a unified data structure that can represent jobs from both systems. Distinguish them clearly in the UI, perhaps with a "Source" field (e.g., "Scheduler" vs. "Web Chat"). Ensure that status, worker, and elapsed time are displayed consistently. This provides a single pane of glass for all ongoing work.
    *   **Verification:** The "Jobs" tab in the web UI should display active and recently completed jobs from both systems without duplicates or omissions.

2.  **Create a Legacy-to-WebBob Job Adapter:**
    *   **Task:** Develop a component or function that can translate a legacy job specification from `next-prompts/INDEX.md` or `services/backlog.json` into a new `task_queue` entry.
    *   **Details:** This would be the first step toward unifying the systems. Instead of `services/jobs.py` launching a `screen` session directly, it would call this adapter to enqueue the task in `state/queue.jsonl`. The `services/job-runner.sh` would then pick it up like any other Web Bob task. This leverages the new system's resilience (retries, fallbacks) for scheduled work.
    *   **Proposed Patch:** A new function in `services/jobs.py` could handle this translation and queuing.

    ```python
    # In services/jobs.py

    def enqueue_legacy_as_web_task(spec, lane):
        """Translates a legacy job spec into a new Web Bob task queue entry."""
        from state import task_queue
        from state.api_tasks import normalize_kind

        # This is a simplified example. Full implementation would need
        # to map projects, evidence, and other fields correctly.
        prompt = spec.get("prompt", "")
        kind = spec.get("kind", "coding")
        # Use existing logic to determine if it's an API-only task
        kind = normalize_kind(lane, task_queue.task_kind(kind, prompt), prompt)

        # The root path would need to be correctly determined
        root_path = Path(__file__).resolve().parents[2]

        return task_queue.enqueue(
            root=root_path,
            conversation_id="legacy-scheduler",
            request_id=spec["id"],
            prompt=prompt,
            worker=lane,
            kind=kind,
            title=f"{spec.get('project', 'Scheduled')}: {spec['id']}",
            publish_project=spec.get("project") if spec.get("publish_new_draft") else None,
            draft_pr=spec.get("publish_new_draft", False)
        )
    ```

3.  **Refactor State Management:**
    *   **Task:** Consolidate high-level state updates into `state/ledger.py`.
    *   **Details:** Modules like `webchat/handback.py` and parts of `services/runtime.py` write directly to their own state files. The `state/ledger.py` module is emerging as a central place for "current status" (`NOW.md`, `BOB-CATCHUP.md`). Refactor other components to call functions in `state/ledger.py` to report their status, rather than writing files directly. This makes the overall system state more coherent and easier to track.
    *   **Verification:** A test that simulates a job completion should show that `state/ledger.py` is called and that `NOW.md` reflects the change, without the job-running logic directly touching `NOW.md`.
