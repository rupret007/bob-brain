## Concrete Findings from Available Evidence

### 1. `services/jobs.py` — Job Lifecycle & Lane Assignment

**Finding (F-JOBS-01):** `can_assign()` at line ~195 has a WebJam-only mutex for coding jobs:
```python
if spec["kind"] == "coding" and spec["project"] == "WebJam":
    if any(r.get("project", "").startswith("WebJam") and r.get("kind") == "coding" for r in active):
        return False
```
This blocks all WebJam coding jobs when ANY WebJam coding job is active. No per-PR isolation exists despite PR-specific worktrees.

**Risk:** PRs #159 and #160 (both WebJam CI fixes) cannot run concurrently even if they target different branches.

**Regression Test Draft:**
```python
# services/test_jobs_can_assign.py
def test_webjam_coding_mutex_allows_different_prs():
    """WebJam coding PRs on different branches should not block each other."""
    from jobs import can_assign
    health = {lane: {"state": "ready"} for lane in ("cursor", "codex", "gemini", "minimax", "claude")}
    
    # Simulate PR #159 already running
    active_159 = [{"project": "WebJam", "kind": "coding", "engine": "cursor", "job_id": "cursor-webjam-ci-159-abc123"}]
    
    spec_160 = {"project": "WebJam", "kind": "coding", "id": "webjam-ci-160", "pr": 160}
    # BUG: This returns False, blocking PR #160
    result = can_assign(spec_160, "cursor", active_159, health)
    assert result == True, "Different WebJam PRs should not block each other"
```

### 2. `services/lanes.py` — Lane Capacity & Concurrency

**Finding (F-LANES-01):** `slot()` context manager uses `shared=True` for API lanes (gemini/minimax) but the exit stack logic at line ~75 is fragile:
```python
with lock("lane-" + lane, blocking=False, shared=True):
    for index in range(limit):
        # ...
        stack.enter_context(lock("lane-" + lane + "-" + str(index), blocking=False))
```
If multiple indices are checked sequentially and all are busy, the function raises `BlockingIOError` but the outer shared lock is still held during the iteration.

**Risk:** Under high concurrency, API lane slots may not release promptly.

**Regression Test Draft:**
```python
# services/test_lanes_slot.py
def test_slot_releases_on_exhaustion():
    """All slots must release before BlockingIOError propagates."""
    import threading, time
    from lanes import slot
    
    acquired = []
    def hold():
        with slot("minimax") as s:
            acquired.append("thread1")
            time.sleep(0.5)
    
    t = threading.Thread(target=hold)
    t.start()
    time.sleep(0.1)  # Let thread1 acquire
    
    # Thread2 should fail but not block thread1
    try:
        with slot("minimax") as s:
            acquired.append("thread2")
    except BlockingIOError:
        pass
    
    t.join()
    assert acquired == ["thread1"], "Slot should not leak to blocked caller"
```

### 3. `services/backlog.json` — Priority Inversion

**Finding (F-BACKLOG-01):** `queue_specs()` in jobs.py merges backlog.json entries with INDEX.md entries, but the sorting is unstable:

Items with identical (project, priority) have no secondary sort key (e.g., spec_id or enqueue time), so queue order is non-deterministic between ticks.
