This report provides a whole-repo audit and implementation plan for the ongoing task `lane-webbob-texting-disk-evidence-fix-2003`. The original prompt for this task was not supplied; this analysis is based on the task name and the provided source code.

The task name suggests a fix related to evidence handling, particularly for API workers ("texting" is a colloquial term for API model interactions in this project) when the source of evidence is on "disk". The audit confirms a potential failure path where an API worker, assigned to review an ongoing coding job, will fail if that coding job has not yet created its private Git worktree on disk.

### Findings

1.  **Evidence Path Failure**: API workers (`gemini`, `minimax`) assigned to review an ongoing job (via `source_job_id`) depend on the source job's `worktree` path to gather repository evidence. The function `services/dispatch_worker.py:report_repository` correctly identifies the `worktree` path from the source job's record in the task queue. However, if the source job is still `queued` and has not been claimed and started, its `worktree` has not been created on disk. In this scenario, `report_repository` returns `None` for the repository path.

2.  **Preemptive Rejection**: The `services/dispatch_worker.py:execute` function for the API worker then immediately fails with a `ResultRejected` exception, stating "The assigned source job has no available worktree for repository evidence". This happens before any evidence is collected or any call is made to the model.

3.  **Race Condition**: This creates a race condition. If the API worker's task is claimed and executed before the source coding job's task, the API worker will fail. The system relies on the coding job's worker (`codex`, `cursor`) starting first to prepare the necessary directory structure.

4.  **Existing Coverage**: The test `services/test_replay_completion.py:ReportRepositoryTests.test_missing_source_worktree_stops_before_evidence_or_model_call` explicitly validates this failure behavior. It confirms that if a source job has no worktree, the API report job fails before calling the model. This indicates the behavior is known and tested, but it may not be the desired long-term behavior.

The implementation plan below proposes adding a regression test to `services/test_api_workers.py` to highlight this race condition more directly within the API worker test suite, using a `queued` source job. The proposed fix is to change the API worker's behavior from immediate failure to a "busy" state, allowing it to wait and retry, giving the source job time to initialize its worktree.

    def test_api_worker_fails_if_source_job_worktree_is_not_on_disk(self):
        repo = self.repo()
        (self.core / "services").mkdir()
        (self.core / "services/projects.json").write_text(json.dumps({"Web Bob": {"repo": str(repo)}}))

        # Enqueue a coding job, but do not claim or run it. Its worktree does not exist yet.
        source_job = queue.enqueue(self.root, "conversation", "source", "Improve Web Bob", kind="coding")
        self.assertIsNone(source_job.get("worktree"))

        # Enqueue an API audit job linked to the queued coding job.
        api_job = queue.enqueue(self.root, "conversation", "api-report", "Audit the ongoing work",
                                worker="gemini", kind="audit", source_job_id=source_job["id"])

        api_claim = queue.claim(self.root, "gemini")
        self.assertEqual(api_job["id"], api_claim["id"])

        # Execute the API worker. It should fail because the source worktree is missing.
        with patch.object(dispatch_worker, "ask") as ask:
            exit_code = dispatch_worker.execute(api_job["id"], api_claim["claim_token"])

        self.assertEqual(exit_code, 1)
        ask.assert_not_called()

        result = queue.tasks(self.root)[api_job["id"]]
        self.assertEqual(result["status"], "failed")
        self.assertIn("The assigned source job has no available worktree for repository evidence", result["error"])
