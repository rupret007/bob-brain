This report provides a whole-repo audit and implementation plan for the ongoing task `lane-webbob-texting-smoke-replay-fix-1901`.

### Audit Findings

The original prompt for this task was not supplied. Based on the task name and the provided evidence, the audit focused on potential regressions in task dispatch, completion, and replay safety, particularly concerning API workers.

1.  **Replay Safety:** The system has robust replay protection for new task submissions. `state/task_queue.py`'s `enqueue` function uses a deterministic UUID based on `conversation_id` and `request_id` to prevent duplicate task creation. This is covered by tests such as `webchat.test_dispatch.ChatDispatchTests.test_duplicate_request_creates_one_task` and `webchat.test_integrate_2057.PinnedDeploymentAssignments.test_attempt2_turn_one_dispatches_from_the_matching_release_pins`. These tests confirm that resubmitting a request with the same ID does not create new tasks.

2.  **Dispatch and Completion:** The dispatch logic in `services/dispatch_worker.py` correctly handles various task kinds, including API-only reports. It prepares evidence, constructs a detailed prompt with deliverable requirements, executes the worker, and then subjects the answer to a strict acceptance process via `services/result_acceptance.py`.

3.  **Result Acceptance:** The `result_acceptance.py` module contains strong deterministic checks (`check_deliverables`, `check_completion_json`) that run before any semantic review. These guards enforce the presence of required deliverables like regression test drafts, an actionable plan, and a specific completion JSON block for "independent subtask" assignments. Evidence from `services/test_result_acceptance.py` and `services/test_regression_drafts.py` shows these checks correctly reject incomplete or malformed reports.

4.  **Identified Gap:** While the system correctly rejects reports that *omit* the mandatory `Action plan:` section, it does not enforce that the `Change:`, `Validation:`, and `Exit condition:` values appear on the same line as their labels. The current implementation in `result_acceptance.check_deliverables` uses a regex that can incorrectly pass a plan where values are on subsequent lines. This could lead to ambiguity or mis-parsing by downstream tools or human reviewers. This appears to be a regression or an incomplete implementation of the intended deliverable contract.

### Implementation Plan

The plan is to strengthen the validation for the `Action plan:` section to enforce that all values are on the same line as their respective labels. This ensures the report structure is consistent and machine-readable as intended by the prompt contract.
