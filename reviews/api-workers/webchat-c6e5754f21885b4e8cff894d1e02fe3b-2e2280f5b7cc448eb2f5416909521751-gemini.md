An audit of the Web Bob repository reveals a systemic issue where API-only workers (`gemini`, `minimax`) are incorrectly assigned repository context from unrelated, concurrently running jobs. This breaks task isolation and leads to incorrect or irrelevant outputs, as workers are prompted with evidence from a task they were not assigned to. The ongoing task `# lane-webbob-texting-screen-isolation-fix-1403` points to this problem.

### Audit Findings

1.  **Incorrect Context Assignment**: `webchat/worker_assignment.py` in the `plan()` function identifies "ongoing work" to provide context for new API worker assignments. It correctly finds active coding jobs (e.g., from `state/task_queue.py` or `ps` output). However, it then passes the `job_id` of this unrelated coding job as `source_job_id` when enqueuing the new API report task.

2.  **Erroneous Evidence Gathering**: `services/dispatch_worker.py` in `report_repository()` uses this `source_job_id` to look up the source job's repository and worktree. Consequently, `services/api_worker.py`'s `evidence()` function creates a snapshot of the *unrelated coding job's repository*, not the repository relevant to the new assignment (e.g., the main Web Bob project).

3.  **Symptom - Irrelevant Reports**: This causes the API worker to receive a prompt containing files and context from a completely different task and project. For example, a request to audit "Web Bob" might receive evidence from an active "WebJam" coding job, leading to a useless report about WebJam. This was a key factor in the `lane-webbob-texting-screen-isolation-fix-1403` incident, where workers were confused by mismatched evidence.

4.  **Correct Behavior (No Active Jobs)**: When no coding jobs are active, `webchat/worker_assignment.py` correctly falls back to providing context based on the project itself (e.g., from an open screen lane or the deployed checkout). In this case, `source_job_id` is `None`, and `dispatch_worker.py` correctly identifies the "Web Bob" project repository, leading to correct evidence gathering.

### Implementation Plan

The fix is to stop linking new API report assignments to unrelated active jobs. The `source_job_id` should only be used when a task is a genuine sub-task of another. An assignment to "audit ongoing work" is a new, independent task *about* that work, not a child process that should inherit its private worktree.

The proposed patch modifies `webchat/worker_assignment.py` to pass the project context via the prompt text and removes the incorrect `source_job_id` linkage.

```patch

+++ b/webchat/worker_assignment.py
@@ -211,7 +211,7 @@

                              prompt=prompt, source_job_id=source["id"]))
+    # The source_job_id links a new report to an unrelated job's repository,
+    # breaking isolation. The ongoing task's context is already in the prompt.
+    for pkg in packages:
```
