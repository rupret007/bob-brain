Report on "Web Bob unblock 1035"

As requested, this report provides a whole-repo audit and an implementation plan for the ongoing task "Web Bob unblock 1035".

**Limitation:** The original prompt for this task was not provided in the evidence. This audit is therefore based on an inspection of the repository snapshot to identify the most critical areas for improvement and potential blockers to system reliability and forward progress.

### Whole-Repo Audit

The repository contains a sophisticated AI orchestration system ("Mini conductor") and a user-facing web chat interface ("Web Bob"). The system is undergoing a significant architectural transition from a monolithic conductor (`loop.sh`) to a distributed, four-service model (`job-runner`, `reviewer`, `dashboard-updater`, `watchdog`) as described in `BUILD-SERVICES.md` and `HARDEN-AND-CURSOR.md`.

**Key Architectural Strengths:**

1.  **Durable State:** The use of append-only journal files (`.jsonl`) for jobs (`services/jobs.py`), tasks (`state/task_queue.py`), and financial ledgers (`services/budget.py`) provides resilience against restarts and crashes.
2.  **Core File Protection:** `bootstrap.py` implements a crucial syntax gate and a `git restore` mechanism from a `last-good` tag, protecting the core services from invalid self-modifications.
3.  **Resource Management:** API access is centralized through `services/lanes.py` with shared locks, and spending is strictly controlled by `services/budget.py`, preventing overruns.
4.  **Isolated Workspaces:** Jobs are executed in private Git worktrees (`services/workspaces.py`), preventing concurrent modifications and ensuring task isolation.

**Identified Risks & Potential Blockers:**

1.  **Dual Orchestration Paths:** The system has two parallel task execution systems:
    *   The "legacy" project system managed by `services/jobs.py` and `services/worker.py`.
    *   The "Web Bob" system managed by `webchat/task_dispatch.py`, `state/task_queue.py`, and `services/dispatch_worker.py`.
    While they share some primitives (lanes, budget), they have separate queues, worker implementations, and state management. This duality increases complexity, complicates resource scheduling (e.g., "one WebJam coder at a time"), and creates a risk of inconsistent behavior and race conditions.

2.  **Incomplete Service Migration:** The `BUILD-SERVICES.md` task outlines the creation of four core services. However, the repository snapshot does not contain the specified output files: `services/job-runner.sh`, `services/reviewer.sh`, `services/dashboard-updater.sh`, and `services/watchdog.sh`. The `job-runner.sh` file that does exist appears to be a simple loop that calls `runtime.py`, which in turn calls `jobs.py` for a `tick`. This suggests the migration to the independent, `screen`-based service architecture is either in-progress or has not been completed as specified.

3.  **Redundant Entry Points:** Files like `loop.sh`, `run-tick.sh`, and several scripts in `compat/` are marked as compatibility shims or legacy. While many now defer to the new `bootstrap.py` entry point, their continued existence creates confusion and a risk of being invoked incorrectly, bypassing the new service-oriented architecture.

### Implementation Plan

The most critical "unblocking" action is to complete the architectural migration to the unified, four-service model. This will resolve the dual-orchestration problem and simplify the system, making it more reliable and maintainable.

**Actionable Plan:**

1.  **Unify Task Queues:**
    *   **Goal:** Create a single, unified scheduler that can draw work from both project backlogs (`services/backlog.json`, `next-prompts/INDEX.md`) and the Web Bob queue (`state/task_queue.jsonl`).
    *   **Proposal:** Modify `services/jobs.py` (the primary scheduler in the new model) to also poll the Web Bob task queue. When a Web Bob task is selected, it should be executed via `services/dispatch_worker.py`. This consolidates all scheduling decisions into one component, allowing it to enforce global constraints like "one WebJam coder".

2.  **Complete the Four-Service Implementation:**
    *   **Goal:** Implement the four independent services as specified in `BUILD-SERVICES.md`.
    *   **Proposal:** Create the shell script wrappers for each service. These scripts will be simple loops that call the appropriate Python function via `bootstrap.py`, touch a heartbeat file on success, and sleep. This decouples the services from each other and enables the watchdog to monitor them effectively. A proposed patch for `services/job-runner.sh` is provided below as a template.

3.  **Deprecate Legacy Entry Points:**
    *   **Goal:** Remove or clearly disable old entry points to prevent accidental use.
    *   **Proposal:** After the unified scheduler is active and the four services are running, modify legacy scripts like `loop.sh`, `run-tick.sh`, and `compat/ops-queue-refill.py` to exit immediately with a message pointing to `services/start-all.sh`.
