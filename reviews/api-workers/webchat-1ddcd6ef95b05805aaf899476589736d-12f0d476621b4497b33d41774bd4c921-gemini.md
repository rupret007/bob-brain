### Audit Findings

The current task dispatch system is robust, with several key strengths: durable task queues, worker isolation via private Git worktrees, result acceptance gates, and specific handling for API-only workers. However, the analysis reveals a potential reliability issue and an area for improvement in how new work is assigned to API workers.

1.  **Finding: Redundant Context for API Worker Assignments.** The `webchat/worker_assignment.py` module correctly identifies ongoing work to provide context for new API-based review or audit tasks. The `deployed_project_context` function serves as a fallback to inspect the running "Web Bob" checkout when no other work is active. However, this fallback logic is overly specific and duplicates the more general mechanism in `services/dispatch_worker.py` which already determines the correct repository for a report. This creates two separate paths for context gathering, increasing maintenance overhead and the risk of divergence.

2.  **Finding: Inefficient Fallback for API Worker Assignments.** When no active jobs are found, `webchat/worker_assignment.py` checks for unverified `screen` sessions as a last resort to find a project repository. This is less reliable than using the project catalog and deployment pins. A more direct approach would be to create a placeholder source job that represents the project context, allowing the standard `report_repository` logic in `dispatch_worker.py` to handle it uniformly.

### Implementation Plan

To address these findings, the following plan proposes centralizing the logic for API worker context and simplifying the assignment process. This involves creating a placeholder "context" task and removing the redundant context-gathering code from `webchat/worker_assignment.py`.

#### 1. Create a Placeholder "Context" Task

A new, non-executable task kind, `context`, will be introduced. When `worker_assignment.plan` finds no active jobs but needs to assign work (e.g., against the deployed Web Bob checkout), it will first enqueue a `context` task. The subsequent API worker jobs will then reference this `context` task via `source_job_id`.

This change leverages the existing `report_repository` logic in `services/dispatch_worker.py` to correctly resolve the repository from the source job, eliminating the need for special-case code in the assignment planner.

#### 2. Refactor `webchat/worker_assignment.py`

The `plan` function will be updated to use this new `context` task mechanism. The `deployed_project_context` function and the logic for inspecting unverified `screen` sessions for context will be removed. The planner will instead create a single `context` task and link all new API jobs to it.

This simplifies the assignment logic, making it more reliable and easier to maintain by relying on the centralized and robust repository resolution already present in the dispatch worker.
