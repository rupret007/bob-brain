An audit of the Web Bob dispatch system reveals a robust, multi-layered architecture for task queuing, execution, and result handling. The system correctly distinguishes between tool-using workers (Codex, Cursor) and API-only workers (Gemini, MiniMax), enforcing capabilities at multiple stages. The core dispatch loop in `services/dispatch_worker.py` and the durable queue in `state/task_queue.py` provide a solid foundation with claim fencing, heartbeats, and state transitions.

However, several areas present opportunities for hardening and improved reliability.

### Concrete Findings

1.  **Redundant Worker Validation:** Worker validation logic is present in both `state/task_queue.py` (`validate_worker`) and `webchat/task_dispatch.py` (`validate_worker`). While `task_dispatch.py` calls the queue's function, it also contains its own validation logic that could diverge. This redundancy increases maintenance overhead. The single source of truth for worker capabilities and compatibility should be `state/task_queue.py`.

2.  **Inconsistent `max_attempts` Logic:** In `state/task_queue.py`, the `enqueue` function calculates `max_attempts` as `max(MAX_ATTEMPTS, len(worker_order(kind)))`. This ensures a task can try every compatible worker. However, the `transition` function's `retry` logic uses a hardcoded `MAX_ATTEMPTS` to determine if a task should be terminally failed: `status="failed" if row["attempts"] >= row.get("max_attempts", MAX_ATTEMPTS) else "queued"`. This could cause a task to fail permanently before it has a chance to try all compatible workers if `len(worker_order(kind))` is greater than the default `MAX_ATTEMPTS` (3).

3.  **Potential for Stale Project Context in Worker Assignments:** `webchat/worker_assignment.py` uses `observe_work` to find ongoing tasks and then creates new API-based analysis jobs sourced from them. The `deployed_project_context` function provides a fallback to inspect the currently deployed code if no active jobs are found. However, there's a risk that the "ongoing task" prompt (`source["prompt"]`) could be stale or not fully representative of the work being done, especially for long-running jobs. The plan should prioritize using the live repository state from the source job's worktree when available, rather than just its initial prompt.

### Implementation Plan

Based on these findings, I propose the following improvements.

**Proposed Regression Test for `max_attempts`**

A test case should be added to `services/test_dispatch.py` to verify this behavior.

```python
# In services/test_dispatch.py, within DispatchTests class

    def test_retry_uses_per_task_max_attempts_before_failing(self):
        # A kind with more than 3 compatible workers, e.g., 'analysis'
        self.enqueue(request="analysis-task", kind="analysis")
        row = queue.tasks(self.root)[self.enqueue.id]
        self.assertGreater(row.get("max_attempts"), 3)
        
        for i in range(row.get("max_attempts")):
            claim = queue.claim(self.root, "codex", now=100 + i*10, allow_fallback=True)
            self.assertIsNotNone(claim, f"Failed to claim on attempt {i+1}")
            result = queue.transition(self.root, claim["id"], claim["claim_token"], "retry", now=101 + i*10, error="test failure")
            if i < row.get("max_attempts") - 1:
                self.assertEqual(result["status"], "queued")
            else:
                self.assertEqual(result["status"], "failed")

        final_row = queue.tasks(self.root)[row["id"]]
        self.assertEqual(final_row["status"], "failed")
        self.assertEqual(final_row["attempts"], row.get("max_attempts"))
```

**3. Enhance Worker Assignment Context**

The `plan` function in `webchat/worker_assignment.py` should be modified. When a source job from the durable queue (`state/task_queue.py`) has a `worktree`, the API worker's evidence-gathering process in `services/dispatch_worker.py` (`report_repository`) should be instructed to use that specific worktree. This ensures the analysis is performed on the exact code state the primary worker is using, not just the base repository state. `report_repository` in `services/dispatch_worker.py` already contains logic to use the `worktree` from a `source_job_id`, so the primary change is to ensure this path is robustly tested and utilized. No code change is proposed, but this highlights a critical interaction that must be maintained.
