Based on the supplied repository snapshot, here is a whole-repo audit and implementation plan for the ongoing "Web Bob integrate" task.

### **1. Audit Findings**

As the original prompt for the "Web Bob integrate" task was not provided, this audit is based on an inspection of the project's current code and state. The primary focus appears to be on creating a reliable, resilient, and verifiable deployment and task execution system for the Web Bob chat interface.

#### **1.1. Strengths**

*   **Resilient Orchestration:** The architecture has matured from a single loop to a four-service model (`job-runner`, `reviewer`, `dashboard-updater`, `watchdog`) as described in `services/README.md`. This design, managed by `services/start-all.sh`, improves resilience by isolating failures. The watchdog service provides automated recovery.
*   **Durable State Management:** The system uses append-only journals (`.jsonl` files) for critical state, such as `state/task_queue.py` for Web Bob tasks and `services/jobs.py` for legacy jobs. This is a robust pattern that prevents state loss on restart and allows for reliable recovery, as seen in `jobs.recover()`.
*   **Automated and Verifiable Deployments:** The `webchat/deploy_integrate.py` and related scripts represent a sophisticated, evidence-based deployment process. Key features include:
    *   **Review-Gated Releases:** Deployment is tied to a specific, clean, and tested draft PR.
    *   **Live Session Replay:** The system replays historical user sessions (`webchat/fixtures/integrate_sessions_0927.json`) against the new release to verify behavior.
    *   **Automated Rollback:** On failure, the deployment script is designed to restore the previous version and its state snapshots, ensuring stability.
*   **Core Integrity Protection:** `bootstrap.py` implements a critical safety gate. It performs syntax validation (`bash -n`, `py_compile`) on core scripts before execution and uses `git` to automatically roll back to a `last-good` tag upon detecting a committed but invalid change. This prevents a broken deployment from taking the whole system down.
*   **Secure and Metered API Access:** All model interactions are routed through metered transports (`services/api.py`, `services/lanes.py`, `services/budget.py`). This provides centralized control over spending, enforces caps (e.g., the $48 MiniMax cap), and handles credentials securely without exposing them in process arguments.

#### **1.2. Risks and Areas for Improvement**

*   **Complexity and Divergence:** The system now has two parallel task/job systems: the legacy project-based system in `services/jobs.py` and the new Web Bob system in `state/task_queue.py` and `services/web_dispatch.py`. While `jobs.import_legacy()` provides a migration path, the dual systems increase complexity and the risk of inconsistent behavior.
*   **State Synchronization:** The new `state/ledger.py` and `state/alignment_events.py` introduce a third layer of state, intended to be a "single source of truth." However, it appears to be synchronized *from* the live operational state (`live_dashboard.py`, `ledger.sync_from_live_ops`). This one-way sync could lead to discrepancies if the primary state sources (e.g., `jobs.jsonl`, `queue.jsonl`) are ever restored from a backup, leaving the ledger out of date.
*   **Manual Handoff Points:** The system relies on `handback/BOB-STATE.md` for context handoff to a different agent (Bob). This file is updated by `handback.py` but is fundamentally a human-readable summary. A failure to update this file or a misinterpretation by the receiving agent could break context continuity.
*   **Inconsistent Credential Loading:** Multiple scripts load credentials directly from `conductor/keys.env` (e.g., `compat/ask-gemini.sh`, `services/common.sh`, `webchat/api_call.py`). While secure, this pattern is repeated. A single, unified entry point for sourcing credentials would be more maintainable.

### **2. Implementation Plan**

This plan focuses on integrating and unifying the disparate state and execution systems to improve reliability and reduce complexity.

#### **2.1. Unify Task and Job Schedulers**

The highest-value improvement is to merge the legacy `services/jobs.py` scheduler into the modern `services/web_dispatch.py` and `services/job-runner.sh` loop.

1.  **Modify `services/job-runner.sh` Cycle:** The main loop in `services/runtime.py`'s `runner_cycle()` should become the sole owner of all task scheduling.
2.  **Integrate Legacy Queue:** The logic from `jobs.tick()` for reading `next-prompts/INDEX.md` and `services/backlog.json` should be moved into `runtime.runner_cycle()`.
3.  **Adapt Records:** When a legacy job is selected, create a corresponding record in `state/task_queue.jsonl` instead of `jobs.jsonl`. This makes it visible to the unified Jobs tab and uses the modern, more resilient `dispatch_worker.py` execution path.
4.  **Deprecate `jobs.jsonl` for New Work:** New jobs will only be written to `state/queue.jsonl`. The `jobs.jsonl` file will be read-only for recovering and migrating in-flight work.

#### **2.2. Make `state/ledger.py` the Authoritative Source**

Refactor state-mutating operations to write to the `state/ledger.py` system first, and then have operational modules read from it or be updated by it.

1.  **Reverse Sync Direction:** Instead of `ledger.sync_from_live_ops`, create a `live_ops.sync_from_ledger` function. The dashboard and status reports should render directly from the ledger's state.
2.  **Centralize Task Creation:** All new tasks, whether from Web Bob (`task_queue.enqueue`) or legacy prompts (`jobs.create_record`), should first create an entry in the `state/ledger.py` and `state/alignment_events.py` system. The operational `queue.jsonl` record should be derived from this entry.
3.  **Update Handback:** Modify `handback.py` to read directly from `state/ledger.py` to build its summary, removing the dependency on parsing `BOB-STATE.md`.
