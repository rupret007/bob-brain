### 1. Whole-Repo Audit: Integration & Deployment

The repository contains a sophisticated, review-gated deployment and integration system primarily for the `webchat` service. The process is designed for safety, with explicit rollback mechanisms and extensive live verification.

**Key Components:**

*   **Deployment Orchestrators (`webchat/deploy_*.py`):** The core of the integration process resides in a set of scripts: `webchat/deploy_integrate.py`, `webchat/deploy_parity.py`, `webchat/deploy_replies.py`, and `webchat/deploy_replyq.py`. These scripts automate a release by:
    1.  Verifying prerequisites (e.g., clean git state, correct draft PR status, passing offline tests).
    2.  Creating a rollback snapshot of the current working code.
    3.  Restarting the `svc-webchat` and `svc-job-runner` services to activate the candidate code (`webchat/deploy_parity.py:restart`).
    4.  Executing a suite of live verification checks against the newly deployed version.

*   **Live Verification (`webchat/live_*.py`, `webchat/integration_rubric.py`):** After a deployment, the orchestrator runs a series of "proof" scripts. These are not simple unit tests; they are live integration tests that interact with the running service.
    *   `webchat/deploy_integrate.py` and `webchat/deploy_replyq.py` perform an "exact session replay," using historical user messages from fixtures (`webchat/fixtures/integrate_sessions_0927.json`) to ensure the new code replies correctly.
    *   `webchat/integration_rubric.py` defines the success criteria for these replays, checking not just for a successful reply but also for correct operational effects (e.g., were the right jobs queued?).
    *   Other scripts like `webchat/live_redeploy_check.py` and `webchat/live_dispatch_proof.py` verify core functionalities like status reporting and job dispatching against the live, redeployed service.

*   **Task & Service Management (`state/task_queue.py`, `services/dispatch_worker.py`, `services/runtime.py`):** The integration process correctly targets the two key services (`svc-webchat` for the UI/API and `svc-job-runner` for dispatching background work) for restarts. It relies on the durable task queue defined in `state/task_queue.py` to verify that actions taken in the UI result in correctly queued jobs.

**Findings:**

1.  **Strength: Safety First.** The entire process is built around verification and the ability to roll back. Creating a snapshot before touching the live services is a critical safety feature that is correctly implemented. The use of live, post-deployment checks is a robust way to ensure a release is truly working.
2.  **Strength: High-Fidelity Testing.** Replaying real user sessions (`deploy_integrate.py`) is a powerful integration testing method that goes far beyond typical unit or component tests. It verifies the end-to-end flow from user input to durable system state changes.
3.  **Area for Improvement: Redundancy in Deployment Scripts.** There are four separate `deploy_*.py` scripts. While they target different releases (e.g., `webbob-integrate-2057`, `webbob-replyq-1856`), they share a significant amount of boilerplate for setup, verification, restart, and rollback. This suggests a pattern of copying and modifying scripts for each release, which can lead to maintenance overhead and divergence.
4.  **Area for Improvement: Brittle Test Fixtures.** The session replay tests in `webchat/deploy_integrate.py` and `webchat/integration_rubric.py` depend on hardcoded session IDs and expected turn counts. As seen in `integration_rubric.py`, the rubric is manually extended for different sessions (`b33fac...`, `8126...`). This is fragile and requires manual updates as test cases evolve.

### 2. Implementation Plan

The goal is to unify the deployment logic and make the integration testing more data-driven and maintainable.

**Step 1: Unify Deployment Logic**

Create a single, parameterized deployment script that can handle different release types. This script would consolidate the common logic from the existing `deploy_*.py` files.

*   **Proposed Action:** Create a new script, for example, `webchat/release.py`. This script would accept arguments specifying the candidate code path, the draft PR, and a configuration file for the specific verification steps to run.
*   **Details:** The core `restart` function from `webchat/deploy_parity.py` can be moved into a shared module. The new `release.py` would handle:
    1.  Reading a release configuration (e.g., `releases/integrate-2057.json`).
    2.  Performing prerequisite checks (git, PR, offline tests).
    3.  Creating the rollback snapshot.
    4.  Calling the shared `restart` function.
    5.  Iterating through the verification steps defined in the config file and executing them.
    6.  Triggering a rollback if any step fails.

**Step 2: Create Data-Driven Integration Tests**

Decouple the integration test logic from the test data (the user sessions and expected outcomes).

*   **Proposed Action:** Modify `webchat/deploy_integrate.py` (or its successor from Step 1) to load session replay scenarios from a directory of JSON files instead of having them hardcoded.
*   **Details:**
    *   Create a directory like `webchat/fixtures/replay_scenarios/`.
    *   Each file in this directory (e.g., `session_b33fac.json`) would contain the list of user messages and a corresponding rubric defining the expected outcomes for each turn (e.g., `expected_kind: "assign"`, `expected_job_count: 2`, `expected_projects: ["WebJam", "AdoptIQ"]`).
    *   The test runner would iterate through these files, creating a new conversation for each, replaying the messages, and validating the outcomes against the provided rubric. This makes it easy to add or modify test cases without changing the test execution code. The logic from `webchat/integration_rubric.py` would be generalized to interpret these rubric files.

**Step 3: Draft Initial Test Case Files**

Convert the existing hardcoded session data into the new data-driven format as a proof of concept.

*   **Proposed Action:** Create `webchat/fixtures/replay_scenarios/session_b33fac.json` and `webchat/fixtures/replay_scenarios/session_8126.json` based on the data currently in `webchat/fixtures/integrate_sessions_0927.json` and `webchat/integration_rubric.py`. This validates the new structure and ensures no regression in test coverage.

This plan addresses the identified areas for improvement by reducing code duplication and making the powerful session-replay testing framework more scalable and maintainable.
