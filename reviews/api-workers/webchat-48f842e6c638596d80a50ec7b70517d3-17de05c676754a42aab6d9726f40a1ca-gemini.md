### Audit Findings and Implementation Plan

Based on the repository snapshot, the system has two parallel job-processing mechanisms: a legacy project-based system (`services/jobs.py`) and a newer Web Bob task queue (`state/task_queue.py`). A key risk for blocking behavior is the handling of job closeouts, especially when a job is marked as "blocked". The current implementation of `compat/auto_harvest.py` does not fully align with the hardening goals described in `HARDEN-AND-CURSOR.md` regarding blocked jobs.

**Finding 1: `auto_harvest.py` does not correctly handle `BLOCKER.txt` files.**

The script `compat/auto_harvest.py` is responsible for harvesting job results. Its `_harvest_job` function identifies a `BLOCKER.txt` file and correctly calls `job_event` with a "blocked" status. However, the script then proceeds to call `closeout(job_dir)`, which is defined in `services/jobs.py` as returning `RESULT.txt` or `RESULT.md` if they exist. The `auto_harvest.py` script does not use the return value of `closeout` to alter its behavior. More importantly, the script does not stop after finding a blocker; it continues to attempt to promote deliverables from `queue-ready/`. This could lead to a blocked job being partially harvested, creating an inconsistent state where a task is marked blocked but its outputs are promoted as if it were successful.

This contradicts the rule in `HARDEN-AND-CURSOR.md` (item 3): "writing legacy BLOCKER.txt must NOT mark a job closed; blocked -> state=blocked, retried/escalated, never dropped." While `auto_harvest.py` does set the state to "blocked", its subsequent actions are ambiguous and could be a source of system blockage or incorrect state propagation.

**Proposed Plan:**

I will create a patch for `compat/auto_harvest.py` to ensure that the presence of a `BLOCKER.txt` file results in a clean "blocked" state without any further processing or deliverable promotion. This makes the handling of blocked jobs more robust and prevents inconsistent states.
