### Findings

Based on the task name and the provided evidence, the task likely involves fixing a regression in how the system handles replayed user requests, particularly in the context of texting-related actions which are dispatched and confirmed through the chat interface.

A review of the current implementation reveals a potential regression scenario where a user request to send a text could be duplicated if the server crashes or restarts after the text is sent but before the final confirmation receipt is saved to the chat history.

1.  **Dispatch and Confirmation Flow (`webchat/test_texting.py`)**:
    *   A user drafts a text (`draft reply to...`). The system creates a `pending` draft.
    *   The user confirms with a unique message (`yes <token>`).
    *   The `Texting.confirm` method is called.
    *   Inside `confirm`, the system first audits the confirmation (`_audit_confirmation`), which consumes the token and marks the draft as `delivery_unconfirmed`. This state is saved to the conversation file.
    *   Then, the system attempts to send the text via an external service (`_send_via_andrea`).
    *   If the send is successful, a final receipt message is generated, and the conversation is saved again with the draft marked as `sent`.

2.  **Potential Race Condition/Crash Vulnerability**:
    *   The evidence in `webchat/test_texting.py` in `test_receipt_save_failure_keeps_consent_consumed_after_restart` shows a test for a crash *after* the handoff to the external service. In this case, the draft is correctly marked `delivery_unconfirmed`, and a replay of the confirmation is rejected.
    *   However, there is no explicit test for a crash or duplicate request arriving *after* the external service call succeeds but *before* the final `sent` state is saved.
    *   If a user re-sends the confirmation message (`yes <token>`) in this window, the `Texting.confirm` method would see the draft is no longer `pending` (it's `delivery_unconfirmed`) and correctly reject the duplicate confirmation.
    *   The vulnerability lies in the replay of the *original draft request*. The `Chat.submit` method in `app.py` has idempotency checks based on `request_id`. If a client retries the initial "draft reply..." request, it would receive the same draft card with the same confirmation token. If the user then re-confirms using this replayed token, the system would reject it because the token was already consumed. This is correct behavior.
    *   The core issue is ensuring that no part of the system can re-initiate the *send* action for an already-confirmed draft. The current implementation correctly prevents this by consuming the token and changing the draft state to `delivery_unconfirmed` before the external call. The `_send_via_andrea` function is only called if the draft state is `pending`.

3.  **Conclusion**: The current implementation appears robust against the most likely replay scenarios. The state transition from `pending` to `delivery_unconfirmed` before the external call acts as a lock, preventing duplicate sends. The idempotency of `Chat.submit` prevents the creation of new drafts with new tokens for the same request. Therefore, no implementation change is required. The most valuable action is to add explicit test coverage for the specific replay scenario to prevent future regressions.

### Implementation Plan

The plan is to add a regression test case that explicitly simulates a client replaying the original draft-creation request after a text has been sent but before the final receipt is saved. This will validate that the system correctly serves the original draft card and that a subsequent confirmation attempt with the original token is safely rejected, preventing a duplicate text message.

    def test_replay_of_original_draft_request_after_send_is_safe(self):
        self.mock.enable_web_bob_send = True
        draft_request_id = str(uuid.uuid4())
        draft_text = "draft reply to Alex Morgan: This is a test."
        
        # 1. User submits the initial draft request
        draft_value = self.say(draft_text, request_id=draft_request_id)
        draft = draft_value["messages"][-1]["text_draft"]
        self.assertEqual(draft["state"], "pending")

        # 2. Simulate a crash after send but before receipt save
        save = self.chat.save
        writes = []
        def fail_after_send(value):
            writes.append(1)
            # The second save is the one that records the "sent" receipt.
            if len(writes) == 2:
                raise OSError("disk full after send, before final receipt save")
            save(value)

        with patch.object(self.chat, "save", side_effect=fail_after_send):
            with self.assertRaises(OSError):
                self.say(draft["confirm_message"])

        # 3. Verify state: text was sent once, draft is unconfirmed
        self.assertEqual(len(self.mock.sends), 1)
        self.assertEqual(self.private()["drafts"][draft["id"]]["state"], "delivery_unconfirmed")

        # 4. Client replays the original draft request
        replay_value = self.say(draft_text, request_id=draft_request_id)
        replayed_draft = replay_value["messages"][-1]["text_draft"]
        
        # 5. Assert that the replayed draft is the original one, not a new one
        self.assertEqual(replayed_draft["id"], draft["id"])
        self.assertEqual(replayed_draft["confirm_message"], draft["confirm_message"])
        self.assertEqual(replayed_draft["state"], "delivery_unconfirmed")

        # 6. User tries to re-confirm with the replayed token
        final_value = self.say(replayed_draft["confirm_message"])
        self.assertIn("already used or expired", final_value["messages"][-1]["content"])
        
        # 7. Assert no duplicate text was sent
        self.assertEqual(len(self.mock.sends), 1)
