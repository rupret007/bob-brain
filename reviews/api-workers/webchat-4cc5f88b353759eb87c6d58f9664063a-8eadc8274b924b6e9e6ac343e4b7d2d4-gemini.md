### Audit Report and Implementation Plan for lane-webbob-texting-screen-isolation-fix-1403

This report provides a whole-repository audit and an actionable implementation plan for the ongoing task `# lane-webbob-texting-screen-isolation-fix-1403`.

#### 1. Concrete Findings

The task name `lane-webbob-texting-screen-isolation-fix-1403` suggests a problem with context isolation, specifically involving "texting" and "screen" sessions. My audit of the supplied evidence reveals a potential source of context bleed in the API worker assignment logic.

The function `plan` in `webchat/worker_assignment.py` is responsible for creating tasks for API workers (like Gemini and MiniMax) based on observed "ongoing work". When no active, permission-allowed jobs are found, this function has fallback logic to find a project context. One such fallback uses `live_status_snapshot.observe_work` to identify open `screen` sessions that appear to be project lanes.

As seen in `webchat/test_integrate_2057.py` (`test_frozen_turn_one_with_only_an_unverified_project_lane`), a screen named `lane-webbob-llm-reviews` is sufficient to trigger the creation of API audit jobs for the "Web Bob" project. The prompt generated for these jobs includes the context: "Observed open project lane: ... Its worker activity is unverified; no current task is confirmed."

The problem arises if a `screen` session related to the iMessage texting feature (e.g., a debugging session for `webchat/texting.py`) is named in a way that the system misinterprets it as a "Web Bob" project lane. For example, a screen named `lane-webbob-texting-debug` could be parsed as belonging to the "Web Bob" project. This would cause user requests like "Use Gemini for ongoing work" to incorrectly trigger a full repository audit of the Web Bob project, even if the user's intent was related to the texting feature or if no actual project work was ongoing. This constitutes a failure of context isolation.

The current implementation in `webchat/worker_assignment.py` and its supporting observation modules lacks a mechanism to distinguish project-specific work lanes from other types of `screen` sessions, such as those for debugging or unrelated services that might share a similar naming prefix.

#### 2. Implementation Plan

The goal is to prevent unrelated `screen` sessions from being misinterpreted as a valid context for creating new API worker assignments. This can be achieved by making the project lane identification more specific and robust.

I propose modifying `webchat/worker_assignment.py` to introduce a more explicit check for what constitutes a valid, assignable project lane. The logic should be tightened to only consider screens that are unambiguously associated with project work, rather than any screen that happens to match a project name.

The following patch introduces a new function, `is_assignable_project_lane`, to encapsulate this stricter logic. This function will filter out screens that are likely for debugging, testing, or specific features like texting, preventing them from being used as a source for new, broad project audits.
